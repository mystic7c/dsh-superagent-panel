# 快速开始

把一个空状态的面板配成能自动接单的执行器，通常十分钟以内。本页按顺序给出步骤、每一步的验证方式和常见卡点。

## 0. 前置条件

| 需要 | 用途 |
| --- | --- |
| DeepSeek Harness（含 Web UI） | 宿主，插件跑在里面 |
| Node.js ≥ 22 | Host 半与构建脚本 |
| `octo-cli` 可执行 | 读群消息、回群 |
| 一个有 bot 的 Octo 群 + bot token | 消息来源 |
| 仓库的本地 clone | 执行器在里面开 worktree 改代码 |
| GitLab PAT（`api` 或 `read_api`） | 观察 CI；要写 MR/合并则需要 `api` + 写权限 |

## 1. 保存 Octo token

设置 → 来源 → Octo token → 粘贴并保存。token 写入本机 token 文件（权限 600），面板不回显。
保存后可用「检查新消息」验证是否有效。

## 2. 添加监听群

设置 → 来源 → 「从群列表选择」，或手工填写群 chatId。添加后选择该群接单的仓库并保存绑定。

## 3. 配置仓库

设置 → 仓库 → 「添加仓库」，填写：

- 仓库 id 与显示名称；
- 仓库类型（Web / Oracle EBS 等）与本地路径（必须是已存在的 clone）；
- GitLab 地址与 project 路径、基础分支与目标分支；
- 验证方式（人工验收 / Web UAT）、验收方式（部署后验收 / 合并后验收）；
- 可选：UAT 地址、健康检查地址、设为默认仓库。

保存后在新卡片上保存该仓库的 GitLab token。闸门命令、worktree 等更细的字段仍在 `live.json` 中补，
设置页提供「复制路径」与示例配置。

## 4. 打开引擎

设置 → 来源打开「启用引擎」并保存；设置 → 运行打开执行器，按需开启自动执行。
引擎第一次轮询会初始化游标，不会回放历史消息。

## 5. 验证链路

1. 点顶部「检查新消息」做一次试运行——只读取并评估，不写入状态、不建工单。
2. 在群里发一条明确请求（"把 X 页面的 Y 改成 Z"），概览 / 触发 / 执行会出现对应记录。
3. 也可以在执行页「手工建单」跳过群消息，直接验证执行器与闸门。

## 状态与配置

状态目录默认 `~/.dsh/superagent`，可用环境变量 `DSH_SUPERAGENT_STATE_DIR` 覆盖。

| 文件 | 内容 |
| --- | --- |
| `live.json` | 运行配置（权限 600）。手工改过之后在设置页点「重载配置」 |
| `live-state.json` | 引擎记录，勿手改；`runs` 只存索引行 |
| `inbox.json` | 待办项与已读/已解决状态，可删，重启后按 `live-state.json` 重建 |
| `signal-log.json` | 原始信号与判定；payload 7 天后清空 |
| `operations.json` | 运行台账（steps / trace / gates / report / checkpoint），保留最近 500 条 |
| `acceptance.json` | 每个工单的验收轮次与逐项检查、人审决定 |
| `runs/<runId>.report.jsonl` | worker 报告流，运行结束后并入 `operations.json` |
| `live-history/` | 每次写入前的配置快照（保留 30 份，可在设置 → 变更历史回滚） |
| `octo.token` / `gitlab-*.token` | 令牌文件，权限 600，面板不回显 |

插件没有演示种子：首次启动就是空状态。以前那个「演示管理层」和它的 `/demo/reset` 路由已在 0.9.6 删除。

## 常见卡点

- **群消息不进面板**：先确认「启用引擎」已保存、监听群里包含该群、发送者在允许名单内（或开了「允许任意人类」）。
- **有记录但不建单**：看触发页的评估原因——可能是规则判为忽略，或模型认为请求不明确。
- **执行器不动**：设置 → 运行里看执行器是否开启、是否处于暂停，以及仓库的本地路径是否可写。
- **闸门一直等**：闸门失败会停在「等人放行」，详情页可以重试该闸门或终止。
- **改了 `live.json` 没生效**：设置页点「重载配置」。
