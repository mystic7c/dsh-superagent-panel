# 面板下一阶段：产品评审与落地建议（2026-11-12）

> 来源：用户对 dsh-superagent-panel 的完整评审意见（2026-11-12）。
> 用途：作为后续工单拆解与排期的输入；文中「依据」指向当前实现里的对应位置。
> 状态：**历史输入**。六项改进已在 0.4.19–0.4.38 落地，行为边界见
> [`docs/panel-improvements-2026-11.md`](panel-improvements-2026-11.md)；本文只保留当时的评审视角，不再作为排期依据。

## 一、值得保留并继续强化的设计

- **工单、运行、验收分离。** 一张工单可以多次运行，执行完成与验收通过各有记录，适合真实开发中的反复修改。
- **人工介入已经进入主流程。** 闸门放行、回答问题、追加要求、中断恢复、验收打回都有对应入口。
- **主动接单有证据链。** 原始信号、评估结果、人工标注和重放机制，为以后优化误接单、漏接单提供了基础。
- **交付有工程约束。** worktree、分支守卫、测试闸门、配置快照，已经超出简单“调用模型执行命令”的范围。
- **界面采用待办优先。** 概览强调“需要你处理”，执行页按阶段组织，这很符合一个人管理多个任务的场景。

下一阶段可以围绕一个明确目标：**让你用更少的关注时间，可靠地完成更多工单。**

## 二、功能上，建议优先做这六件事

| 优先级 | 建议 | 主要收益 |
|---|---|---|
| P0 | 修正任务意图分类，允许人工覆盖 | 避免开发任务被当成只读分析 |
| P0 | 补齐运行中停止与停止后的恢复 | 长任务跑偏时能够及时接管 |
| P0 | 区分推送、PR 创建、合并、部署的证据 | 防止界面显示超出实际事实 |
| P1 | 日志页搜索、分页和关联跳转 | 记录增加后仍然容易排查 |
| P1 | 保存交付证据，支持跨轮次比较 | 验收、返工和历史复盘更可靠 |
| P1 | 仓库配置和闸门可视化编辑 | 降低日常维护 live.json 的成本 |

### 1. 任务分类是当前最值得先改的点

当前路由按关键词首次匹配。直接调用现有分类函数，得到：

| 请求 | 当前分类 | 对应 profile |
|---|---|---|
| 修复网页登录失败并补测试 | research | read-only |
| 实现搜索功能 | research | read-only |
| 修复订单保存问题，先分析原因 | analysis | read-only |

原因是“网页”“搜索”“分析”等词优先匹配，覆盖了整句话的开发意图。实际执行是否使用该 profile 还取决于路由模式，但 **auto 路由下会直接影响任务权限和交付类型**。

建议将三个维度拆开：

- **交付目标：** 修改代码 / 输出报告。
- **所需能力：** 读文件、修改文件、执行命令、联网、询问用户。
- **执行后端：** DSH / Codex / Claude。

“修复网页登录问题，需要联网查文档”应是“代码交付 + 联网能力”，而不是整个任务变成 research。

建单时展示自动判断结果，允许修改；已经明确要求修复或实现的任务，不应仅因为包含“分析”就降为报告交付。先用这类混合意图补一组回归用例，比继续增加关键词更有效。

依据：[routing.js](../lib/live/routing.js)。

### 2. 补齐运行中停止，明确暂停的作用范围

当前 live 流程里有闸门阶段的终止和中断恢复，但没有贯穿任意运行阶段的停止入口；旧管理层里的 stop API 不能视为当前执行器已经支持。

建议明确区分：

- **暂停接单：** 暂停消费新请求。
- **暂停派发：** 已有队列保留，正在运行的任务继续。
- **停止当前运行：** 请求 worker 和子进程终止，保存现场。

停止后应显示“哪些动作已完成、是否已经推送、工作树是否保留、能够从哪里恢复”。尤其 push/MR 这样的阶段，需要先确认外部结果再决定下一步，避免把停止简单等同于失败后重跑。

界面中，运行中的工单应该有容易找到的“停止运行”，并显示“正在停止”，直到确实收到停止结果。

### 3. 把交付状态和证据类型分开

当前 GitHub push 路径会保存 `/pull/new/...` 链接，而列表在只有 `webUrl` 的情况下显示“PR 已创建”。

这里存在语义偏差：**创建 PR 的入口链接，不能证明 Actions 已经创建了 PR。**

建议分别记录并展示：

`已推送分支 → 等待创建 PR → 已确认 PR #编号 → 已合并 → 已确认部署 → 已验收`

由托管平台查询结果或 workflow 回执确认真正的 PR。合并检测也逐步补上平台状态，减少对 commit 祖先关系的依赖；目前要求 merge commit 的约束可以继续保留，但应让用户看得见。

这是当前实现里可以直接改善信任感的一项，不只是换文案。

依据：[executor.js](../lib/live/executor.js)、[34-live-ui.js](../client/src/34-live-ui.js)。

### 4. 优先补日志的查找能力

评估页目前只有类型和时间窗口筛选，默认读取最近记录，没有页面级搜索和翻页控件；后端已有 offset/limit，前端可以直接沿用。

建议支持：

- 按文本、仓库、判定原因、时间范围查找。
- “只看模型与规则分歧”“只看人工改判”快捷视图。
- 从评估记录直接定位原始信号、线程和关联工单。
- 筛选条件写入 URL，返回列表时保留位置。

来源、触发、评估三页应该共享同一套查询习惯。现有全局搜索继续用于快速定位对象，页内筛选负责深入排查。

依据：[50-eval.js](../client/src/50-eval.js)。

### 5. 让验收证据在清理 worktree 后仍然可用

目前 diff 主要按需读取工作树，运行台账保留最近 500 条。长期使用时，需要考虑旧工单证据被清理或淘汰的情况。

建议每次交付保存一份有大小限制、经过敏感信息过滤的证据包：

- base/head commit、变更文件摘要及可保留的 patch。
- 闸门命令、结果、时间及对应代码版本。
- worker 总结、验收要求、人工决定。
- MR/PR 和部署证据。

同时提供“本轮与上一轮比较”：新增修改了哪些文件、修复了哪些失败项、哪些要求仍未完成。这样追加要求后的验收会轻松很多。

### 6. 配置界面覆盖高频操作

当前新增仓库、后端路由和配置历史已经具备，但编辑已有仓库、闸门配置等仍需改 JSON。

建议优先提供：

- 编辑仓库，以及停用仓库。
- 闸门名称、命令、目录、超时、失败策略。
- 保存前显示配置差异，并校验命令和路径。
- “测试配置”只执行连接与环境检查，不自动启动开发工单。

已有工单的仓库先停用并保留引用，删除可作为后续能力。

## 三、界面上，重点调整信息组织

现有黑白灰、少量状态色的方向适合开发工作台，可以继续保持。0.4.25 已经修了词汇一致性、重复验收按钮和负载图例，后续更大的收益来自下面这些调整。

### 工单详情围绕当前任务状态展开

当前详情把改动、验收、阶段、闸门、运行、活动、时间线等都放在一个页面。建议保留完整信息，但按状态默认展开：

| 当前状态 | 首屏重点 |
|---|---|
| 执行中 | 当前步骤、最近活动、持续时间、停止入口 |
| 等待回答 | 问题、必要上下文、回答框 |
| 闸门失败 | 失败命令、关键错误、重试或修复入口 |
| 待发布 | 修改摘要、diff、闸门证据、发布入口 |
| 待验收 | 验收清单、交付版本、通过或打回 |
| 已结束 | 交付摘要和证据，历史默认折叠 |

已有的吸顶上下文和主行动可以保留。将“活动、时间线、执行轨迹”归入统一的历史区，分别用筛选查看，减少用户判断应该去哪个区找信息。

依据：[58-ticket-detail.js](../client/src/58-ticket-detail.js)。

### 概览把人工待办做得更具体

每条待办建议回答四件事：

> 什么卡住了 → 为什么需要我 → 已等待多久 → 我可以做什么

例如：

> 登录修复 · 单测失败 · 等你处理 18 分钟
> `auth.test.js` 有 2 项失败；自动修复已用完 1 轮
> **查看失败**　重试闸门

统计信息放在这些待办之后。已有成功率和耗时之外，可以增加“人工处理次数”“等待人工时长”“首次验收通过率”，更直接反映插件是否帮你省事。

### 执行列表增加具体的下一步描述

保留现有阶段分组，但在状态旁补充实际阻塞点：

- 执行中：正在跑后端测试。
- 等你处理：需要回答数据库连接方式。
- 待验收：PR 已合并，等待你确认页面效果。
- 排队：等待仓库执行槽位。

这比继续增加状态标签更容易阅读。

### 来源、触发、评估保留独立页面，但加强一条链路内的导航

先加一个统一的关联条：

`原始消息 → 判定及原因 → 工单 → 本次运行`

等实际使用证明页面切换仍然过多，再考虑合并为“接单中心”。目前直接合并三个页面，会增加改造成本，也可能削弱已有排障能力。

## 四、工程上值得同步整理的部分

- **收拢状态转换规则。** `engine.js` 约 2900 行、`executor.js` 约 1900 行，后续加入停止、恢复、重试时，适合先提取状态转换与动作前置条件，统一前后端对“允许做什么”的判断。
- **为外部动作建立幂等记录。** 推送、创建 PR、回群、验收等动作应能记录“请求已发出但结果未知”，重启后先核对结果。
- **为存储增加归档与一致性检查。** 现在每个 JSON 文件的原子替换是有用的基础，但不等于跨台账事务；先补启动时对账和证据保留策略，再根据数据规模判断是否迁移 SQLite。
- **让验证环境可复现。** 当前渲染脚本依赖 `/tmp/sa-harness`，还读取本机状态构建部分 fixture。建议固化依赖，并逐步改成独立 fixture，方便干净 clone 和 CI 运行。
- **同步文档。** README 仍写 0.4.18，部分测试数字和安装说明滞后；成熟度文档也仍把已实现的 hybrid 接单列为未实现。最好让版本与验证数量从实际结果生成。
